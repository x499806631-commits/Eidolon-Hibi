# 01: 看板读预先汇总的表（乙方案）

**What to build:** 写运行记录时顺手累加进按 15 分钟一格的汇总表，看板只读汇总表，打开的耗时不再随运行记录的数量增长。2026-10-19 讨论过，用户决定先只做甲（在库里汇总，见下），乙方案留到需要时再做。

**Blocked by:** None

**Status:** done

## 为什么会要做

甲（`feat/dashboard-sql-aggregation`，提交 `8e63fbb`）把看板改成在 SQLite 里分组汇总，不再逐条读进内存：内存不会再撑爆，结果和旧版逐字段一致。但每次打开仍要把范围里的每一行过一遍，耗时和运行记录的数量成正比。

2026-10-19 在线上库快照上量的（服务器 2 核，负载约 1.0）：

| | 运行记录 | 服务调用 | 旧版 | 甲 |
|---|---|---|---|---|
| 24h | 2.7 万 | 13.6 万 | 3.5s | 1.6s |
| 7d | 3.2 万 | 16.0 万 | 3.3s | 3.0s |
| 90d | 3.2 万 | 16.1 万 | 4.0s | 2.3s |

三个范围的行数差不多，耗时却忽高忽低（7d 比 90d 还慢），是线上服务同时在抢那 2 个核造成的噪声，看量级就好。

慢在服务调用表的三遍：按 10 列分组一遍、延迟和首字时间的分位数（窗口函数排序）各一遍，每遍约 0.5s / 16 万行。试过 `temp_store = MEMORY`、加大 `cache_size`、按主键区间扫，最多省 20–30%，没有采用。

用量从 2026-10-18 下午 5 点（北京时间）起涨到每小时约 1500 条运行记录、每天约 13.6 万次服务调用。照这个量估：一周后「7 天」约 10 秒；攒满 90 天（`KEPT`）后「90 天」要一两分钟，而且每次都和通话抢 CPU。

**什么时候该做：** 打开「7 天」超过 5 秒左右，或者想看「90 天」却等不起的时候。

## 方案草图

- 汇总表按 15 分钟一格（所有时区的偏移都是 15 分钟的整数倍，管理者时区的整点、整天都能对上 `dashboard.stretches`）。一格里的分组键大致就是现在的 `CallGroup` / `RecordGroup` 去掉 `stretch`、换成格子的开始时间。
- 写运行记录时在同一个事务里 UPSERT 累加（`ActivityLog._insert` / `_insert_call`）。原始的运行记录照样留 90 天，后台用户页、价格页和测试（`ActivityLog.since`）照样用它们；过期删除时汇总表一起删。
- 次数、失败数、用量、花费照样精确（花费是用量乘单价，按格加总后再乘，结果一样）。
- 分位数（延迟、首字时间、开口时间、通话时长）只能近似：每格记各个对数区间里有几次，看板按区间估。
- 活跃用户数不能按格相加：另记「哪一格里有哪些用户」（`INSERT OR IGNORE`），按范围 `COUNT(DISTINCT)`；好感度一节的「冷却的用户数」同理。
- 新表、启动时从现有运行记录回填，部署前要手动备份库。
- 接口字段不变，前端不动。

## 已定的（2026-10-20 拷问）

1. 运行记录和服务调用都汇总（运行记录 90 天攒满约 230 万行，也会拖慢）。
2. 延迟、首字时间、开口时间、通话时长的 P50/P90/P95 改为近似：每格按对数区间（宽 2^(1/16)，误差约 ±2%）记次数。推翻 2026-10-19「保持精确」。通话时长按 `DURATIONS` 各档的计数单独记、保持精确；改 `DURATIONS` 要重新回填。
3. 15 分钟一格，格子开始时间存 UTC 的 epoch 秒。
4. 范围的开头往前取整到格子边界（最多多算 15 分钟），接口的 `from` 是取整后的时刻；不从原始记录补开头的半格。
5. 活跃用户、冷却的用户精确：另记「哪一格有哪个用户、这一格里冷却过没有」，按范围、按趋势的每一段 `COUNT(DISTINCT)`。这张表加进 `ANONYMIZED_USER_DATA`，删号时一起换成匿名 id。
6. 回填在启动时的迁移里同步做：汇总表空、原始记录不空时，`INSERT … SELECT … GROUP BY` 一次做完。部署前手动备份。
7. 搭话被回了（`store.py` 里 `UPDATE activity_records SET answered = 1`）时，在同一个事务里把汇总的计数从没回挪到回了。
8. 现在逐行扫的 `_tally` 搬进测试当参照：同一批记录，次数、用量、花费、人数完全相等，分位数在误差以内。部署前在线上库快照上再对拍一次。
9. `billed_models`、用户页、`since` 照读原始记录；原始记录照留 90 天，过期时汇总表按格一起删；接口字段不变，前端不动。
10. 回滚不加自动处理：回滚到旧版后再升级，要先手动删掉汇总表，启动时会重新回填。写进部署文档。
11. 15 分钟一格之外再按 UTC 的天记一层。线上 24 小时按 15 分钟汇总约 5.8 万行（运行记录的分组 9300、服务调用的分组 1300、格 × 用户 4100、分位数区间约 4.3 万），只比原始的 14.8 万行少一半多；按天时运行记录的分组和分位数区间每天各约 900 行。要按趋势分段的（服务调用的分组、每段的回合数和通话数、每段的人数）读 15 分钟的格子；只要整个范围的（运行记录的分组、四种分位数、通话时长分档、活跃用户和冷却的用户）读中间的整天加两头不满一天的格子，口径和 Q4 一样。

## 怎么量

在线上库上对拍新旧两版的办法（2026-10-19 用过，做完已经清理）：

- 用 SQLite 的 backup 接口在后端容器的 `/tmp` 里拍一份快照（对线上库只读，300 MB 约 5 秒），新旧两版都用这份快照、同一个固定的「现在」去算，再逐字段比 JSON（浮点相对误差 1e-9 以内算一样）。
- 新代码打成 tar 传进容器的 `/tmp/<目录>/eidolon`，用 `PYTHONPATH` 指过去。**跑的脚本不能放在这个目录里**：Python 会把脚本所在目录排在导入路径最前面，跑「旧版」时也会导入新包。
- 构造后端时把 `catalog.refresh_soon` 换成空函数，免得第一次跑去拉价格目录，第二次的单价不一样。

### 实现说明（票 01）

- `activity.py`：新表 `record_rollups`、`taken_rollups`、`user_rollups`、`call_rollups`、`spread_rollups`（`ROLLUPS`），触发器 `record_rollups_answered`。`_insert` / `_insert_call` 写完一行就用 `_roll_up_records` / `_roll_up_calls`（`WHERE id = ?`）累加；启动时五张表全空就用同一套 SQL（`WHERE true`）回填（`_roll_up_all`），两条路共用一份汇总口径。`tally(moment, starts)` 不再收 `durations`，`DURATIONS` 从 `dashboard.py` 挪到 `activity.py`；新函数 `range_start`。
- `dashboard.py`：`from` 是 `range_start(now - span)`。`database.py`：`user_rollups` 进 `ANONYMIZED_USER_DATA`，其余四张进 `NOT_USER_DATA`。
- 判断：
  - 分位数的区间里另记最小、最大值，排名落在区间第一个或最后一个时给真值，所以数据少时和以前完全一样，现有测试里的精确延迟断言不用改。
  - 搭话被回用触发器，不在 `store.py` 里写汇总代码；删表时要连触发器一起删，部署文档的脚本里写了。
  - 原始记录照旧按 `<= now - 90 天` 删；汇总表的格和天要整段过完才删，所以 90 天范围开头那一格里，可能还算着原始记录里已经删掉的几条，和第 4 条「最多多算 15 分钟」是同一个口径。`test_records_are_forgotten_after_90_days` 和 `test_each_range_takes_the_turns_since_that_long_ago` 按这个口径改了时间。
- 线上快照对拍（2026-10-20）：四个范围逐字段一致，分位数最多差 2.19%；耗时 24h 1.36s → 0.19s、7d 3.47s → 0.07s、30d 3.53s → 0.05s、90d 2.44s → 0.05s；回填 3.1s；每个回合（4 次服务调用）写入 1.71ms → 2.16ms。

### 审查留下的判断题（没改）

- 「空值存成 '' 或 -1」在写入端（`_RECORD_KEY`、`_roll_up_calls`）和读出端（`_tally` 里的 `NULLIF`）各写一遍，以后加分组列要改三处（表结构、`_RECORD_KEY`、`_tally`）。
- `for length in (SLOT, DAY)` 出现四次，`_forget_before` 按有没有 `length` 列手动拆表名；部署文档里的删表脚本也写死了表名。
- measure 的名字（`latency`、`first_token`、`time_to_speak`、`lasted`、`lasted_within`）是裸字符串，没有 `Literal`；「时长分档」叫 `DURATIONS`、`_BAND`、`lasted_within` 三个名字。
- `dashboard.py` 先算一次 `range_start`，`tally` 里又算一次（结果一样）。
- 「汇总表 / 格」没单独进 GLOSSARY，只写在「看板」词条里。
