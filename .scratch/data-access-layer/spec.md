# 架构加深（第十轮）：数据访问层——一个写线程，事件循环上不碰库

Status: ready-for-agent

这是 #165 第二节的 2.1（deepening-10）。设计经 grilling 定下，结论记在 #165 的评论「进度：第二节 2.1 数据访问层（deepening-10）拷问完成」里。术语以 `GLOSSARY.md` 为准，本轮不改 GLOSSARY；设计词汇（module、interface、seam、adapter、depth、locality）取自 `codebase-design` skill。决定本身记在 ADR-0028，删账号的 checkpoint 一节补进 ADR-0006 的修订。只改后端。

## Problem Statement

所有通话的音频都跑在同一个事件循环上，库却有很多地方还在这个循环上读写，或者在循环上等别人的锁：

- **库被拆成约 18 条连接，每条配一把只管自己的 `threading.Lock`。** 模块之间真正的排队靠 SQLite 30 秒的忙等。
- **循环上直接写库的地方还有很多**：
  - 记录回合（`_record`：消息、照片、事件、好感度）；
  - 回合和通话结束时的结算（退还用量、写运行记录）；
  - 通话结束时记下通话、结算每日任务和成就；
  - 搭话结算；
  - 照片保存（约 150 KB）；
  - 登录回调（建用户、建会话）；
  - 后台保存配置（顺带 `gifts.notice`）；
  - 回合之外每一次计费的服务调用（记忆整理、标题、试调、探测）。
- **线程拿着锁时，会把循环一起卡住。** 循环上这些调用拿的是 `threading.Lock`。housekeeping 线程每 10 分钟拿着 `ActivityLog` 和 `UsageLimiter` 的锁批量删除；删账号在线程里拿着 `Store` 的锁跑 0.5–1 秒。这期间循环上碰到同一把锁的调用都在等，等待期间所有通话的音频也停着。
- **读库用的 `asyncio.to_thread` 零散地包在调用点外面**（第一节 c 步的窄版）：回合开头的读取在一处，搭话的读取又用一个 lambda 把同一组数据打包成元组读一遍。新代码只要漏包一处，就又回到循环上，没有任何东西会报出来。
- **跨模块的写入凑不成一个事务。**
  - 记录回合时，消息和好感度分两条连接、两次提交。
  - 送礼要提交 5 次，只有第一次有补偿；用重置卡也是这个结构。
  - `Happenings` 借 `Gifts` 的连接写；数据包导入另开一条连接，绕开所有锁，整个导入过程（连解压照片在内）一直拿着 SQLite 的写锁。
- **删账号的 `wal_checkpoint(TRUNCATE)` 碰到开着的读事务**（比如备份的 `VACUUM INTO`）就会等，期间挡住所有写入，最多 30 秒。等满放弃时不报错，WAL 里还没拷回的帧留着，被删的数据可能还在主库文件里，ADR-0006 的「真删」没有兑现。本地测量：读者开 40 秒时，12192 帧只拷回了 129 帧。

## Solution

库只有一个入口：一个数据访问层。

- **写**：整个进程只开一条写连接，放在一个专用线程上；所有写入交给它，按顺序一个一个执行。
- **读**：用几条只读连接，在线程池里跑。
- **对外接口**：各模块碰库的公开方法都改成 `async`，SQL 留在模块里，由层把连接交给它。事件循环上没有任何地方再拿连接，也不再等任何锁。

这样做的结果：

- 跨模块的写入可以放进同一个事务，补偿写入不再需要。
- 写完要通知通话模块时，由循环上的调用方在 `await` 之后去通知。
- 长写入要么分批，要么在写任务之外先准备好，不长时间占着写线程。
- 删账号的 checkpoint 短超时、没做完就重试。

用户看到的行为不变。看得出来的差别有三处：

- 通话不再因为别人删账号、后台清理、写入排队而卡顿；
- 一个回合要么完整记下，要么完全没记；
- 删账号后，WAL 里的旧页几秒内就被清掉，不会悄悄留下。

## User Stories

1. 作为通话中的用户，我希望别的用户删账号时，我这通电话的声音不卡。
2. 作为通话中的用户，我希望后台每 10 分钟一次的清理不让声音卡一下。

24. 作为部署者，我希望停机一天后，第一次清理分批进行，不会一次占住写线程几百毫秒。
25. 作为部署者，我希望命令行工具（同步剧情、恢复等）照样能用。
26. 作为部署者，我希望库文件、表结构不变，部署时不用迁移数据。
27. 作为开发者，我希望在事件循环上拿连接时，测试直接失败，CI 能拦下新加的漏网之处。
28. 作为开发者，我希望线上万一漏了一处，只记一条 error、照常执行，不让回合或通话失败。
29. 作为开发者，我希望模块对外只有 async 一种用法，「在循环上必须 await」由类型保证。
30. 作为开发者，我希望跨模块的事务通过「把同一条连接传给对方的事务体」来组合，不靠嵌套回调和补偿写入。
31. 作为开发者，我希望写库的函数里不调回调、不读循环那边的状态，写入的后果作为返回值交给调用方。
32. 作为开发者，我希望调用点上不再有零散的 `to_thread` 包读库。
33. 作为开发者，我希望各模块不再自己开连接、自己加锁，关闭顺序也不再要小心排。
34. 作为开发者，我希望数据访问层的规则（顺序、取消、关停、检查、日志、checkpoint 重试）经它自己的 interface 测。

## Implementation Decisions

### 数据访问层

一个新的 module，放在现有的 `database` module 旁边（`USER_DATA` 等表的登记仍在原处），对外大致是这个样子（grilling 时定的形状，名字可以在实现时调整）：

```python
class Database:
    async def read(self, body: Callable[[Connection, *A], T], *args: *A) -> T
    async def write(self, body: Callable[[Connection, *A], T], *args: *A) -> T
    async def checkpoint(self) -> None   # 清空 WAL：短超时，没做完就之后重试
    async def close(self) -> None        # 先跑完已交的写任务，再关所有连接
```

- **写**：只有一条写连接，放在一个专用线程上，不占默认线程池。`write` 把事务体排进队列（先来先做），在写线程上用 `with conn:` 跑：正常返回就提交，抛异常就回滚，然后把结果或异常交回给 `await` 的一方。
- **读**：4 条 `query_only` 读连接（服务器 2 核），由层管理，从默认线程池里借用。`read` 在一条读连接上开一个读事务跑事务体，所以一次 `read` 里读到的是同一份快照。`ActivityLog` 原来那条单独的快照读连接就不再需要了。
- **连接的设置**：每条连接仍由 `connect` 打开（WAL、`synchronous=NORMAL`、`secure_delete`、`foreign_keys`）。各模块要用的自定义 SQL 函数（如 `spread_bucket`），由层注册到每一条连接上，不再只注册在某一个模块的连接上。
- **建表和迁移**：仍然写在各模块里。启动时按现在的构造顺序，作为写任务依次执行。
- **取消**：事务体一旦交给写线程，就一定执行完（提交或回滚）。`await` 的一方被取消，只是收不到结果，任务本身不撤回。所以等待方被取消时，按「可能已经写进去了」处理。第一节 c 步给「放行被取消」补的那次结算照样保留。
- **关停**：`close` 先不再接受新的写任务，跑完队列里已有的，再关写连接和所有读连接。`Backend.aclose` 原来那些按模块倒序、有的拿锁有的不拿锁的关闭，都收成这一处。
- **事件循环上的检查**：在事件循环所在的线程上拿连接（不论读写），测试里抛异常，线上记一条 error、照常执行。检查做在层交出连接的地方，所以凡是经过这一层的路径都会被检查到。
- **慢任务日志**：一次写任务排队等待超过 200 ms，或执行超过 200 ms，记一条 warning，带任务名（事务体的限定名，如 `Store._add_turn`）和当时队列的长度。读的时候所有读连接都被占着、要等超过 200 ms，也记一条。只写日志。

### 模块的形状

- **对外一律 async**：各模块凡是碰库的公开方法都改成 `async def`，方法体基本只有一句 `await self._db.write(self._add_turn, …)` 或 `await self._db.read(…)`。现有的 SQL 搬进私有的同步事务体（参数是层交来的连接），SQL 本身不改写。
- **去掉自己的连接和锁**：各模块不再自己开连接、不再持有 `threading.Lock`。只为保护内存里的状态、而且只在循环上用的锁（如 `Store` 的「正在进行的回合」计数）改成不加锁。在循环之外也要用的内存状态，由实现时逐个判断。
- **涉及的模块**：
  - `Store`（约 51 个方法）、`ActivityLog`、`Affinities`、`Gifts`、`Happenings`（连同成就）；
  - `Memories`、`UsageLimiter`、`ReachOuts`、`Announcements`、`Sponsor`、`Prices`；
  - 价格目录（`Catalog`）、`Backups`、`LiveConfig`、剧情库（`StoryCorpus`）、两个 `EmbeddedTexts`；
  - `DataPackages`。

  `Catalog` 自己的刷新线程改成 asyncio task，取数仍走 HTTP，写库经过这一层。
- **跨模块组合**：一个事务体要写别的模块的表时，调用那个模块的事务体，把同一条连接传过去，不经过对方的 async 方法。`Gifts.reward` 现在接收的 `due(db, now)` 就是这种形状，保持不变。
- **删掉调用点上的 `to_thread`**：
  - 回合开头读的那一组（是否已结束、对话记录、上次联系、好感度、能不能发照片、制作人档案），和搭话读的是同一组数据，收成一个读方法，回合和搭话共用。
  - 其余调用点上包读库的 `to_thread` 一律删掉。
  - 纯 CPU 的活（Pillow、numpy 相似度、压缩打包）照样放在线程里，它们不碰连接。
- **同步的 handler 和依赖**：碰库的同步 FastAPI handler 和依赖改成 `async def`，包括 `signed_in_user`、`admin_user`、`gifts_api`、`announcements_api`、`photos_api`、后台用户页和 `sponsor_api`。数据包导出改成：先用一个读任务读出这位用户的数据，再在线程里打包。
- **命令行**：用 `asyncio.run` 走同一个层。只有 `restore` 换库文件时，用它自己的连接。

### 写完通知：写入返回结果，由调用方通知

- 事务体里不调任何回调，也不读循环那边的状态。
- **冷却**：`Affinities.change` 原来在提交后调 `on_cooldown` 的监听器，最终走到 `Calls.cooled`。现在删掉 `on_cooldown`，`change` 的返回值里已经带着「这一步让她进入了冷却」和冷却到什么时候。记录回合的一方在循环上 `await` 完写入后，自己告诉通话模块。通知仍在原来那个 task 里，所以通话模块读到的 ContextVar（「正在进行的是不是这一回合」）和现在一样。
- **她结束对话**：`engine.on_ended` 本来就在回合记下以后、在循环上调用，保持不变。
- **搭话**：`Store.add_reach_out` 现在拿着锁在线程里调 `Calls.in_call`，读循环那边的通话集合。改成由调用方先在循环上查好「她在不在通话里」，作为参数传进去。
- **数据包导入后补记忆向量**：导入返回后，在循环上启动补向量的 task；补向量本身的读写经过这一层。

### 跨模块的写入合成一个事务

- **记录回合**：消息、照片、对话事件、`answered` 标记，加上好感度变化，再加上每日任务和成就的结算，合成一个写任务、一个事务。原来 `Affinities` 拿着锁去回调 `Store.add_turn`、两次提交的做法去掉。
- **送礼**：扣礼物、记下送礼、好感度、每日任务和成就，合成一个事务。原来「后面失败就把礼物放回去」的补偿写入删掉。
- **用重置卡**：同上，补偿写入删掉。
- **删对话**：本来就在一个事务里，改成经过这一层，不再绕开别的模块。
- **不合并的**：运行记录和服务调用记录（`ActivityLog`）仍然单独写、失败只记日志。不能因为记账失败让回合、送礼失败。这包括结算（退还用量、写运行记录）、`daily_task_done` 这类运行记录。

### 先读后写

- **常读偶写的方法**先在读连接上读；需要写的时候再交一个写任务，在写任务里重新确认条件。
  - `use_session` 是典型：每个登录后的请求都会调它，平时只是读，到了续期间隔才写一次，过期时删一次。它在写任务里要再查一次是否已经续过，避免两个并发请求各续一次。这样平时的请求不进写队列，删账号那 0.5–1 秒里，普通请求不用跟着等。
  - 实现时列出所有类似的方法，在票里写明。
- **根据读到的结果决定写不写的**，判断一律在写任务里做，不靠读连接上读到的结果。限额的检查加扣减（`usage.take`、放行）、礼物余额的检查加扣减、成就的检查加解锁，都属于这一类。

### 长写入

- **housekeeping 分批删**：过期用量、运行记录、服务调用记录及其汇总，每批一个写任务，批与批之间让别的写入插进来。每批的行数在实现时测，目标是每批约 50 ms 以内。本地测量：平时每次只要 6–18 ms；停机一天后积压的那一次约 220 ms。所以分批主要是为了停机之后。
- **数据包导入先准备、后写入**：解压、解码照片、校验，都在写任务之外做完。最后用一个写任务、一个事务写进去（对话、消息、事件、照片、通话、搭话、制作人档案、记忆、导入记录）。导入时读 `get_profile` 也放进这个事务里读。每位用户同时只能导入一个，这个限制保持不变。
- **删账号**：
  1. 封禁记录（如果有）和删除本身各是一个写任务、一个事务（按线上最重用户的 2 倍测，约 0.65–0.7 秒）。提交后就回复用户。
  2. 然后调 `checkpoint()`：在写线程上把这一次的忙等调到约 100 ms，再做 `wal_checkpoint(TRUNCATE)`，**检查返回值**。没做完（因为有读者），就过几秒作为新的写任务再试，直到做完。超过约 10 分钟还没做完，记一条 error，然后继续重试。
  3. 层启动时先做一次 `TRUNCATE`，补上上次关停前没做完的。

  这样一次 checkpoint 最多挡住写队列约 100 ms，不会挡 30 秒。
- **备份的 `VACUUM INTO`**：不进写队列，仍在线程里另开一条短命的连接做，和现在一样。（grilling 时说它走读连接；但实测在 `query_only` 的连接上，`VACUUM INTO` 报「attempt to write a readonly database」，所以保留它自己的连接。它不拿任何模块的锁，也不在循环上。）
- **`TurnOutcome.over`**：在循环上先把 `recording.calls` 拍一份快照，再 `await` 写入。第一节 c 步担心的「回合结束后才记下的服务调用和结算抢同一份 `recording.calls`」因此不会发生。

### 不变的部分

- 库文件、表结构、`USER_DATA` 等登记、索引，都不变，部署时不需要迁移。
- 健康检查仍然另开只读连接、不经过这一层。
- 照片仍存在库里（ADR-0024），只是保存改成写任务。
- `assembly.THREADS = 32` 保持不变：读任务和纯 CPU 的活仍然用默认线程池。

## Testing Decisions

- **好的测试**只经 interface 断言看得见的结果：HTTP 的响应、库里留下了什么、日志里写了什么、并发时谁等了谁。不检查内部字段，不 monkeypatch 某个方法跑在哪个线程。先写会失败的测试（`/tdd`），再改实现。
- **接缝 1：现有的 HTTP 接缝**（`make_client` → 真实的 `assembly.build`，约 99 个测试文件），这是主要的接缝。
  - 行为不变的部分由现有用例保证。
  - `conftest` 默认打开「在循环上拿连接就抛异常」的检查，这样这些文件跑到的每条路径都同时在防回退。
  - 新的行为测试优先写在这里：
    - **记录回合是一个事务**：让记录中途失败（比如成就结算抛异常），消息、好感度、任务进度都没有留下。
    - **送礼、用重置卡同上**：中途失败时，礼物和卡都还在，好感度不变。
    - **冷却照样挂断**：一个回合让她进入冷却，进行中的通话被挂断，结束原因和现在一样。可以仿照现有的冷却挂断测试。
    - **删账号不挡别人**：在另一条连接上开着读事务的同时删账号，另一位用户的回合照常记下，不用等那个读者结束；读者结束后，WAL 被清空。
    - **会话续期**：两个并发请求只续一次。
    - **限额**：两个同时到达的回合，不会都占到最后一个名额。
- **接缝 2：数据访问层自己的 interface**（读、写、checkpoint、关闭）。只测它自己的规则：
  - 写入按交的顺序执行；读不用等写，长写入进行中照样能读；
  - 事务体抛异常就回滚，异常交回给 `await` 的一方；
  - `await` 的一方被取消，任务照样执行完，写入照样提交；
  - `close` 先跑完已交的写任务，之后再交的被拒；
  - 在循环所在的线程上拿连接会被发现：测试模式抛异常，线上模式记 error 并照常执行；
  - 排队或执行超过阈值、读池要等，都记 warning，带任务名和队列长度；
  - 有读者时 `checkpoint` 不挡后面的写入，读者结束后重试成功；一直做不完时记 error；启动时补做一次。
