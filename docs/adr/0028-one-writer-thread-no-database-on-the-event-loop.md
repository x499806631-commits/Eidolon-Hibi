# 库只有一条写连接，写入在专用线程上排队；事件循环上不碰库

所有通话的音频都跑在一个事件循环上，库却被拆成约 18 条连接，每条配一把只管自己的锁，有不少写入直接在循环上做（#165）。线程里的长操作（删账号、清理）拿着锁时，循环上碰到同一把锁的调用也跟着等，等待期间所有通话的声音都停着。

所以库只有一个入口：整个进程只开一条写连接，放在一个专用线程上，所有写入按交来的顺序一个一个执行。读用几条只读连接，在线程池里跑。各模块碰库的公开方法一律改成 async，SQL 留在模块里，由这一层把连接交给它。在事件循环的线程上拿连接，测试里直接失败，线上记一条 error。SQLite 本来就只允许一个写者，这样做只是把「在 SQLite 里忙等」换成「在一个看得见的队列里排队」。

## Considered Options

- **保留各模块的连接和锁，每个公开方法外面包一层 `to_thread`**：改动最小，但锁照样要抢，模块之间还是靠 SQLite 30 秒的忙等排队，跨模块的事务也照样做不了。
- **一个读写不分的共享连接池**：写入照样在 SQLite 里抢写锁，2 核机器上得不到并发，反而多了一层复杂度。
- **换 PostgreSQL**：约 340 处 SQL 和 ADR-0006 靠 `secure_delete` 兑现的「真删」都要重做；而瓶颈在「库的调用在事件循环上」，换了库也一样有。
- **对外同时提供同步和 async 两套方法**：同步的 handler 不用改，但每个方法都有两种调用方式，「在循环上必须 await」就没有类型来保证了。

## Consequences

- 一个长写入会让后面的写入排队，但只是排队，不会卡住事件循环。长的清理分批做；数据包导入先在写任务之外准备好再写；删账号的 checkpoint 短超时、做不完就重试（见 ADR-0006 的 2026-10-21 修订）。排队或执行超过 200 ms 记 warning。
- 跨模块的写入可以放进同一个事务：一个事务体调用另一个模块的事务体，把同一条连接传过去。记录回合、送礼、用重置卡各是一个事务，不再靠补偿写入。运行记录仍然单独写，记账失败不影响回合。
- 事务体里不调回调，也不读事件循环那边的状态。写入的后果（比如这一回合让她进入了冷却）作为返回值交给调用方，由调用方在循环上通知通话模块。
- 交给写线程的任务一定执行完，等待的一方被取消也不撤回；关服务时先跑完队列再关连接。
- 健康检查和备份的 `VACUUM INTO` 仍然另开连接，不经过这一层：前者为了在这一层卡住时也能报不健康，后者因为 `VACUUM INTO` 在只读连接上做不了。
- 这仍是单进程。要让部署不断通话、或者一台机器撑不住时，再考虑拆出通话进程或换库（#165 第三步）。
